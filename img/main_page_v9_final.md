# HSM: Hyper Stack Manager

**HSM** — это Meta-Orchestrator для гибридных стеков, выступающий в роли "Environment Hypervisor". Он позволяет декларативно собирать рабочее окружение проекта из независимых компонентов на основе единого манифеста.

---

## 🧩 Концепция: Проект как Конструктор

Мы предлагаем смотреть на архитектуру проекта как на **Каркас (Blueprint)**, в котором предусмотрены **Слоты** для установки функциональных **Кубиков-компонентов**.

![Проект как Конструктор](concept-constructor.png)

### 1. Каркас и Слоты (The Skeleton)
Ваш проект — это основной каркас, который взаимодействует с внешним миром через **абстрактные интерфейсы**. В терминологии HSM это **Слоты** (посадочные места):
*   `vector-db-client` — слот для подключения векторной БД.
*   `emb-client` — слот для получения эмбеддингов.

### 2. Кубики-Компоненты (The Bricks)
Это конкретные реализации из нашего **Реестра (Registry)**. Каждый кубик — это независимый Git-репозиторий:
*   **Библиотеки**: Python-пакеты (клиенты, утилиты).
*   **Спутники (Services)**: Автономные сервисы, расширяющие возможности проекта (Docker-контейнеры или изолированные `uv venv`).

### 3. Архитектурный резонанс (Implies)
Реестр HSM — это база знаний о связях. Он позволяет реализовать механику "автоматической сборки сета":
*   **Группы 1-of-N**: Слот, в который можно установить только одну реализацию (например, либо `Qdrant`, либо `Milvus`).
*   **Implies (Синергия)**: При выборе кубика `qdrant-client` (библиотека), HSM автоматически "призывает" в инфраструктуру кубика-спутника `qdrant-service` (контейнер). Они сразу настроены на работу друг с другом.

---

## ⚔️ Механика: Намерение и Реализация

HSM разделяет архитектурное решение и его техническое воплощение, избавляя вас от рутины.

### 1. Намерение (Intent)
Вы не правите конфиги `docker-compose` или `pyproject.toml` вручную. Вы сообщаете системе свое намерение через CLI. Это ваш **Заказ на билд**.
```bash
# "Экипировать проект клиентом Milvus"
hsm select vector-db milvus
```
HSM записывает это в **Манифест** (`hsm.yaml`) — единственный источник правды для вашего окружения.

### 2. Реализация (Implementation)
Команда `hsm sync` запускает **Engine**, который материализует билд:
*   **Синхронизация кода**: Управляет Python-пакетами через адаптер `uv`.
*   **Оркестрация спутников**: Поднимает Docker-контейнеры или VES-сервисы.
*   **Связи**: Автоматически пробрасывает ENV-контекст (HOST, PORT) между компонентами.

## 📦 Состояния кубика: Prod vs Dev

Любой компонент в вашем конструкторе может находиться в одном из двух состояний:

*   📦 **Prod (Стабильный артефакт)**: Использование готового образа или пакета. Максимальная воспроизводимость.
*   🛠 **Dev (Режим Кузницы)**: HSM скачивает исходный код компонента, подключает его к проекту как `editable` и настраивает **Hot-Reload**. Вы правите код компонента — изменения мгновенно применяются в работающей системе.

---

## 🚀 Почему это Level Up для разработки?

*   **Трудности ручной сборки — в прошлом**: HSM берет на себя "ручной клей" между кодом, инфраструктурой и переменными окружения.
*   **VES (Virtual Environment Services)**: Уникальный тип спутника. Полная изоляция Python-сервисов со своими зависимостями (забудьте о конфликтах Pydantic v1/v2).
*   **Atomic Sync**: Синхронизация — это транзакция. Либо всё собралось идеально, либо система откатилась к рабочему состоянию.

## 🏁 Быстрый старт

```bash
# 1. Установка
uv tool install git+https://github.com/VLMHyperBenchTeam/hsm.git

# 2. Инициализация
hsm init

# 3. Сборка первого билда
hsm sync
```
