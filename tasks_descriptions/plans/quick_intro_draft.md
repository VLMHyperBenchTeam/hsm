# HSM за 120 секунд: Быстрое погружение

**Hyper Stack Manager (hsm)** — это инструмент, который объединяет Python-пакеты и сервисы (Docker-контейнеры и uv venv) в единый управляемый и воспроизводимый стек.

В HSM всё строится вокруг **Компонента**. 
> **Компонент** — это вложенный Git-репозиторий, который может быть  Python-пакетом или сервисом (Docker-контейнеры и uv venv). Только Реестр знает обо всех доступных компонентах, позволяя вам собирать из них проект как из конструктора.

---

## 🚀 Фундаментальная идея: Intent vs Artifacts

В основе HSM лежит разделение на **Намерение** и **Реализацию**:

1.  **Намерение (Intent)**: Вы описываете в одном файле `hsm.yaml`, какие компоненты вам нужны и в каком режиме (`dev` или `prod`). Это ваш единственный источник правды.
2.  **Реализация (Artifacts)**: HSM берет на себя "грязную работу" по генерации конфигов для `uv` (`pyproject.toml`) и `docker compose` (`docker-compose.hsm.yml`).

---

## 🛠 Ключевые возможности

### 1. Покомпонентный контроль (Granular Control)
Вы управляете состоянием каждого компонента отдельно:
*   **Режим `prod`**: Использование стабильных версий (пакеты из Git/PyPI или готовые Docker-образы).
*   **Режим `dev`**: Переключение компонента на **локальные исходники** (editable install или `build` контекст).
*   **Смешанный стек**: Можно держать весь проект в `prod`, но одну библиотеку, в которой правите баг, переключить в `dev`.

### 2. Динамический "виртуальный монорепозиторий"
HSM позволяет работать с распределенной системой как с единым целым:
*   **Чистота Polyrepo**: Каждый компонент сохраняет свою историю и независимость.
*   **Удобство Monorepo**: В режиме `dev` HSM собирает нужные компоненты в единое рабочее пространство.
*   **Инфраструктура, следующая за кодом**: Ваше окружение — это не только файлы, но и живые сервисы с автоматической оркестрацией, Hot-Reload и пробросом ENV-контекста.

### 3. Implies: Умные зависимости
Компоненты умеют "заказывать" инфраструктуру. Если вы добавляете библиотеку `auth-plugin`, HSM сам поймет, что ей нужен сервис `postgres`, добавит его в стек и настроит доступы.

### 4. Атомарная синхронизация (Atomic Sync)
Синхронизация — это транзакция. Если зависимости не сошлись, HSM откатит изменения в конфигах. Проект никогда не останется в "полусломанном" состоянии.

## 📦 Анатомия проекта

*   **`hsm.yaml`**: Манифест вашего проекта. Единственный файл, который вы правите вручную.
*   **Реестр (Registry)**: База знаний о компонентах. Описывает, откуда брать код и как запускать сервисы.
*   **Адаптеры**: Модули-исполнители, которые транслируют ваши желания в команды для `uv`, `docker`, `pixi` и др.

## 🎯 Чем является и чем НЕ является HSM?

| ✅ HSM — это | ❌ HSM — это НЕ |
| :--- | :--- |
| **Мета-оркестратор**: Дирижер для `uv`, `docker` и `git`. | **НЕ замена `uv` или `docker`**: Он использует их возможности. |
| **Гипервизор окружений**: Уровень абстракции над вашим стеком. | **НЕ система сборки**: Он не заменяет `make` или `hatch`. |
| **Мост между Кодом и Инфо**: Клей для синхронизации сервисов. | **НЕ CI/CD платформа**: Но он делает её воспроизводимой. |
| **Инструмент для DX**: Убирает рутину переключения контекстов. | **НЕ замена Git**: Он просто автоматизирует клонирование. |

## ❓ Почему не стандартные средства?

### HSM vs Git Submodules
*   **Гибкость**: HSM привязывается к версиям/тегам, а не к жестким коммитам.
*   **On-Demand**: Вы скачиваете только те модули, которые правите сейчас.
*   **Чистота**: Основной репозиторий не знает о внутренностях других проектов.

### HSM vs UV Workspaces
*   **Динамика**: Собирает проект из разных репозиториев на лету, а не требует их наличия на диске.
*   **Умный поиск**: HSM сам находит пути к компонентам через Реестр.
*   **Инфраструктура**: UV не знает про Docker, а HSM — знает.

---

## 🏁 С чего начать?

1.  **Установите HSM**: `uv tool install git+https://github.com/VLMHyperBenchTeam/hsm.git`
2.  **Инициализируйте проект**: `hsm init`
3.  **Добавьте первый компонент**: `hsm library add <имя_из_реестра>`
4.  **Синхронизируйте всё**: `hsm sync`
